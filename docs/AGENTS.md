# AI Agents (MCP)

> 🌐 **English** · [Français](fr/AGENTS.md) · [Deutsch](de/AGENTS.md) · [Italiano](it/AGENTS.md) · [Español](es/AGENTS.md) · [Português](pt/AGENTS.md) · [简体中文](zh/AGENTS.md)

Facet can act as a [Model Context Protocol](https://modelcontextprotocol.io/) (MCP) server, so an MCP-capable AI assistant can search and inspect your library with the same filters the gallery uses. It exposes thirteen read tools that change nothing in your library and thirteen `ui_*` tools that move the browser tab you already have open (page, filters, selection) and never write library data. Tokens that are allowed to can also [change things](#changing-things) (ratings, flags, tags, albums, culling and deletion) and work the [darkroom](#darkroom-culling-groups).

## Enable it

The endpoint is **on by default**. To switch it off, set `viewer.mcp.enabled` to `false` in `scoring_config.json` (see [Agent Endpoint (MCP)](CONFIGURATION.md#agent-endpoint-mcp)) and restart the viewer, or reload the configuration; `/mcp` and every `/api/mcp/*` route then answer 404. Without `viewer.password` the install counts as open, even when `viewer.edition_password` is set, so its tokens are `readonly` unless `viewer.trusted_local_editing` is on. On an open install the endpoint serves only a read-only anonymous key, which grants nothing the open `/api` does not already grant. On an open install, assistant tokens can be minted, listed and revoked only from the computer running Facet (or in an edition session when `viewer.edition_password` is set); any other request is refused with 403.

The endpoint is `POST /mcp` on the viewer's own port: Streamable HTTP, stateless, plain JSON responses. `GET` answers 405. Only the tab bridge, `/api/mcp/bridge`, is a WebSocket; see [Control your open tab](#control-your-open-tab).

## Mint a token

The easiest way is the browser. With `viewer.mcp.enabled` on, open the account menu and choose **Connect an assistant**. Enter a **Name**, pick **What the assistant may do**: **Read and pilot only**, plus **Act as me** or **Full editing** when your session holds that level (a token cannot out-rank the session that creates it), and click **Create token**. The dialog then shows **Paste this into your assistant** with a ready-made prompt that contains the token. It is shown once, so click **Copy prompt**, paste it into your assistant and click **Done**. **Manage tokens (N)** lists your tokens with their last use and revokes one, and a status line says whether this tab is connected so assistants can drive it. The level list is limited to what the server will grant: an open install offers only **Read and pilot only**, **Act as me** appears only on multi-user installs and **Full editing** only in an edition session, which on an open install means a browser on the same computer under `viewer.trusted_local_editing`. The prompt states the level actually granted. On an open install the dialog works only from the computer running Facet (or in an edition session when `viewer.edition_password` is set); from another machine it shows "Assistant tokens on an open install can only be managed from the computer running Facet. Set viewer.password to manage them from another machine." instead of the form and stops asking the server.

Scripted alternative (curl):

An assistant authenticates with a personal token that starts with `fct_`. Mint one with an authenticated request (the token is returned **once**; Facet stores only its SHA-256 hash):

```bash
TOKEN=$(curl -s -X POST http://localhost:5000/api/auth/login -H 'Content-Type: application/json' -d '{"password": "YOUR_VIEWER_PASSWORD"}' | jq -r .access_token)
curl -s -X POST http://localhost:5000/api/mcp/tokens -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' -d '{"name": "my-assistant", "level": "readonly"}'
```

The response carries the plaintext in `token`. `GET /api/mcp/tokens` lists your tokens (never the secret), and `DELETE /api/mcp/tokens/{id}` revokes one. A superadmin can list every owner's tokens with `?all=1` and revoke any of them. Each owner can hold at most 20 live tokens (412 beyond that). These routes refuse an agent's own credential (403), so an assistant can never mint, list or revoke tokens. On an open install (no `viewer.password`) they also answer 403 to any request that does not come from the computer running Facet: one through a reverse proxy (any `Forwarded`, `X-Forwarded-*` or `X-Real-IP` header), one addressed by a LAN IP or a hostname instead of `localhost`, `127.0.0.1` or `[::1]`, or one arriving through Docker's bridge network. Run the recipe above on the Facet host (over SSH on a NAS; in Docker, `docker compose exec facet python -c "import urllib.request ..."`, because the image has no curl) or set `viewer.password`. A session logged in with `viewer.edition_password` is accepted from any machine. A reverse proxy must send `X-Forwarded-For` or `Forwarded`, otherwise it is treated as the local machine.

## Connect your assistant

The prompt the dialog generates holds everything an MCP-capable assistant needs: the server name `facet`, the URL (`http://<host>/mcp`), the transport (Streamable HTTP), the header `Authorization: Bearer fct_...`, the access level granted and a call to the `status` tool to confirm the connection. Paste it into your assistant, or add that server yourself to whichever MCP client you use. Use HTTPS when the viewer is reachable beyond your own machine, since the token travels in a header on every call.

## Permission levels

A token is minted with a grant: `readonly`, `user` or `edition`. The **effective** level is recomputed on every call as the lower of the token's grant and its owner's live level:

- Single-password installs: `user` is capped to `readonly` at mint time, because that mode has no middle level. An `edition` token needs an edition session and works only while the edition password is unchanged.
- Multi-user installs: an `edition` token of a user who is later demoted drops to `user`; a promotion never raises a token above its grant.
- Open installs (no `viewer.password`, even if `viewer.edition_password` is set): tokens belong to a shared `_anonymous` owner and are `readonly`, unless `viewer.trusted_local_editing` is on (next bullet). They can be minted, listed and revoked only from the same computer.
- **Local editing on an open install.** With `viewer.trusted_local_editing` on, the Connect dialog can mint **Full editing** from a browser on the same computer (`viewer.mcp.enabled` is still needed, and so is a token: a token-less call stays 401). That token is `edition` only for `/mcp` requests from the same machine: a loopback peer, an `http://localhost:<port>` or `127.0.0.1` URL and no proxy headers; both `:4200` (the `ng serve` dev proxy) and `:5000` qualify. Any other request with the same token, a LAN client included, resolves to `readonly`, and so does a hostname or `0.0.0.0` URL or a Docker deployment, even if the prompt says Full editing. Any password lowers the token to `readonly`, and clearing the password revives it (the token itself is untouched). Delete tools still need `viewer.mcp.allow_destructive`. Scanning (`start_scan`, `scan_status`) works for the local assistant, like for the local browser, without `viewer.features.show_scan_button`.
- **Caveat.** `ng serve --host 0.0.0.0`, or any unmarked proxy on the same host, lets a LAN client sending `Host: localhost` pass the boundary, leaving only the token to protect `/mcp`.
- Single-password installs have no `user` level: the effective level is `edition` or `readonly`, so the tools marked `user` under [Changing things](#changing-things) also need an `edition` token there. A `user` tool called with a lower token answers `forbidden_level`, saying it needs `edition`.
- Each tool has its own minimum level, checked before anything is read or written; a lower token gets `forbidden_level`.

A token dies automatically when its owner's credentials change: the viewer or edition password in single-password mode, the owner's password in multi-user mode, or the owner's account being deleted. It then answers 401 at the gate.

## Tools

The thirteen data tools are read-only:

| Tool | What it does |
|------|--------------|
| `search_photos` | Filter and sort the library like the gallery, with the viewer's default hide toggles (blinks, bursts, duplicates, brackets, panoramas, rejected) applied unless the filter sets them (reports `hidden_summary`). Shown in your open tab by default (see below); `fields` adds any photo column |
| `semantic_search` | Find photos by meaning, or by words in captions with `scope: "text"` The rows it returns are pinned in the tab. `filters` narrow the search like the gallery's, and each row carries its `similarity`. |
| `get_photo` | Full detail of one photo by its path (the histogram is left out) |
| `get_thumbnail` | Look at one photo: its thumbnail as an image part (`size` 160 to 640, default 512). A smaller size is used when the JPEG would exceed `viewer.mcp.max_image_bytes`; `too_large` when none fits |
| `contact_sheet` | Look at 1 to 16 photos as one numbered grid image (`columns` 2 to 4, longest edge 1024). The text part lists `legend` (tile number to path, in request order) and `unavailable` (tiles left blank because the photo is missing or not visible) |
| `possible_faces` | Faces that look like one recognised person: cosine similarity to the person's centroid, best first, same embedding model only. `scope` is `unassigned` (default), `other_persons` or `all`; `min_similarity` defaults to 0.30; `limit` up to 100. A scan above 192000 faces is refused (`too_large`): narrow it with `scope`, `path_prefix`, `date_from` or `date_to`. The photos are shown in your tab. `candidates` is the count of faces in scope you can see, before the embedding-dimension check; `faces_scanned` is the number of rows actually scored. |
| `similar_photos` | Photos similar to one photo, by visual embedding or by colour; `min_similarity` (0 to 1) sets the floor |
| `filter_options` | The vocabulary a filter accepts: cameras, lenses, tags, persons, patterns, categories, narrative moments, junk kinds, metric ranges |
| `list_persons` | Recognised people, optionally filtered by name |
| `list_albums` | Albums the token's owner can see |
| `library_stats` | Library statistics: `kind` selects the size and score overview (default) or any Stats page data (see below) |
| `status` | Who the token is, its effective level and the server flags and the open tabs it can drive |
| `available_actions` | The jobs that apply to your open tab and this token right now, each with its tools; tools above the token's level are not listed |

In every filter object, `show_rejected` is a boolean: `true` lists only the rejected photos, `false` or omitted gives the normal listing.

## Results are shown in your tab

- `search_photos`, `semantic_search` and `similar_photos` take `show` (default `true`). After a successful first-page search the server shows it in the Facet tab you have open. `search_photos` and `similar_photos` apply the same query to the tab, replacing its filters; `semantic_search` always pins exactly the rows it returned (similarity order, at most `limit`, with or without `filters` or `scope`) as an assistant-chosen list (`shown_in_tab.mode` is `paths`), because the tab's own semantic view is hide-filtered and sorted differently. Either way you see what the assistant found without being asked. Assistants are told never to ask whether to open or show results; `show: false` is for intermediate probes and counts, and the last shown search is what you see.
- The result carries `shown_in_tab`: `{"applied": true, "tab_id", "keys", "total"}`, or `{"applied": false, "reason"}` where the reason is `no_tab`, `bridge_disabled`, `tab_outdated`, `tab_timeout` (the tab may still apply it), `forbidden`, `page_not_first`, `empty_result`, `unsupported_filters` (with `keys`) or `invalid_combination`. A failed show never fails the search. Pass `tab_id` to choose a tab. Every reason: `error` (the show itself failed), `bridge_disabled`, `page_not_first`, `empty_result`, `invalid_combination`, `unsupported_filters` (with `keys`), and the codes the tab bridge returns (`no_tab`, `tab_outdated`, `tab_timeout`, `forbidden`, `invalid_input`, `upstream_error`). When rows are trimmed, `next_page` (with `suggested_per_page`) names the page that continues exactly after the last returned row, or, when pages cannot express that point, `next_offset` gives it as a row offset.
- Only the first page is shown (the tab pages itself as you scroll), and an empty result is not shown, so you keep your previous view. A search using filters the gallery sidebar has no field for (`exclude_tags`, `require_tags`, `is_silhouette`, `junk_kind`, `narrative_moment`, `min_rating`, `min_aggregate`, `show_rejected: true`) is not partially applied.
- A show leaves `/culling`, `/compare` and `/photo` for the gallery, clears a whole-view selection, and on an album page first goes back to the gallery, so an album's saved filters are never overwritten. A search whose count feeds the `expected_count` of a write tool should use `show: false`.
- `ui_show_photos` pins an exact list of photos: the gallery shows them in your order until any filter change replaces the list. `ui_get_context` reports whether a pinned list is shown. The list is plain: it carries no groups, marks or labels. To review a cull plan, the assistant uses `auto_cull`, which opens the plan on the [darkroom](#darkroom-culling-groups) (`/culling`) instead.
- **Plan mode on `/culling`.** `ui_show_culling_plan` (called by `auto_cull` on a dry run) loads an `auto_cull` plan into the darkroom: the same groups, keep/reject borders, loupe and compare as manual culling, with the plan's keepers pre-selected. A banner reads "Assistant plan · x/y confirmed · Exit", each group carries a chip "#n · reason · suggested keep N / reject M", and a dot marks a frame you flipped away from the plan. You confirm group by group with the darkroom's normal Space key, countdown and undo; strictness, sort and threshold are disabled while the plan is shown. **Exit**, or changing the grouping, scope or sort, leaves plan mode. Leaving `/culling` (to open a photo, say) and coming back restores plan mode from the plan already loaded in the tab, with your confirmed x/y kept; a full page reload drops it. A plan the library has outgrown shows an out-of-date notice. Confirms made in plan mode never add highlights. See [Assistant plan mode](VIEWER.md#assistant-plan-mode).
- **Reading your progress.** `ui_get_context.culling` is `null` outside plan mode. In plan mode it returns `{plan_digest, groups_total, confirmed, pending, changed, untouched, plan_truncated}`: `confirmed` lists the plan group numbers whose confirm has landed, `pending` those you flipped away from the plan and have not confirmed, `untouched` counts the rest, and `changed` lists every group whose keepers differ from the plan as `{type, group_id, number, keep_paths, reject_paths}` (`plan_truncated` is `true` when the plan itself was capped at its group or photo limit and so lists only part of the groups; a block too large for one answer, whether cut by the tab's 100 KiB cap or by the server, has its lists shortened and `truncated` set to `true`, the true counts staying in `groups_total`, `confirmed_count`, `pending_count` and `changed_count`). Never re-decide a confirmed group. A confirmed burst or similar group leaves the next preview; a confirmed scene group is not recorded anywhere and may be proposed again, so pass `changed` as `keep_paths` / `remove_paths` on the next dry run and on its apply. `ui_get_context` also returns `culling_defaults`, `{profile, strictness}`: the culling profile stored in this browser, else the page's default strictness (100), which `auto_cull` uses when it is given neither.
- **Dates.** Culling tools (`auto_cull`, `list_culling_groups`, `suggest_culling_profile`) accept an ISO date (`2026-06-01`), an ISO datetime (`2026-06-01T08:30:00` or with a space) or the EXIF form (`2026:06:01 08:30:00`); a date-only `date_to` covers the whole day. Day-granular tools (`library_stats`, `possible_faces`, `cull_report` counts and darkroom sets alike) accept only a date and refuse a time of day as `invalid_input`.
- Rows carry camera, lens, aperture, shutter speed, ISO, focal length and `is_monochrome`. `fields` (on the three search tools) adds any other photo column except the image and embedding data, for example `leading_lines_score`; `learned_score` is filled only when sorting by it. When the byte cap trims rows, the result adds `returned` (and `next_offset` or `suggested_per_page`).
- `library_stats` takes `kind` (default `overview`: size, type counts and score overview). The overview carries a `basis` saying what each total counts: `total_photos` counts the photos you can see within `date_from`/`date_to` and the category (every date and category when none is given), ignores the hide toggles and includes rejected photos, while `type_counts` applies the hide toggles and ignores date and category filters. The other kinds are read-only and return the data of the Stats page; long lists are cut at 50 entries with `truncated: true`:

| Kind | Data |
|------|------|
| `score_distribution`, `top_cameras`, `categories`, `gear`, `stats_settings`, `timeline`, `correlations` | The Stats page panels; they accept `date_from`, `date_to` and `category`. `correlations` also takes `x`, `y` (comma list), `group_by` and `min_samples` |
| `category_breakdown`, `category_weights`, `category_correlations`, `category_overlap` | Category statistics (no parameters) |
| `timeline_dates`, `timeline_months` | Photo counts per day or per month; they need `year` (`timeline_dates` also takes `month`) |
| `timeline_years` | Photo counts per year |

## Control your open tab

Next to the data tools, the server always lists thirteen `ui_*` tools that act on the Facet tab you have open in a browser: they move the page, change the filters or the selection, and read back what you see. They never write library data, so a `readonly` token is enough.

| Tool | What it does |
|------|--------------|
| `ui_navigate` | Go to a page (gallery, persons, albums, stats, ...) |
| `ui_set_gallery_filters` | Merge a patch into the gallery filters and sort (`null` removes a filter, `replace: true` starts from none) |
| `ui_get_gallery_view` | Route, active filters, total matches, the first visible photo paths and the selection count |
| `ui_get_context` | The open page (route), the gallery state (total, loaded count, whether a pinned list is shown), the selection count and the `actions` that apply to your token here; also `focused` (the photo the user is on), `culling` (the assistant's plan on `/culling`: confirmed, pending and changed groups), `culling_defaults` (`{profile, strictness}`) and `user_activity` (what the user did), and accepts `activity_since` (see below) |
| `ui_open_photo` | Open one photo |
| `ui_show_photos` | Show exactly these `paths` (up to 200) in this order as the gallery's list; unreachable ones come back as `missing`. Any filter change replaces the list |
| `ui_select_photos` | Select explicit `paths`, or the whole filtered view with `select_view: true`, with mode `replace`, `add` or `remove` |
| `ui_clear_selection` | Clear the selection |
| `ui_get_selection` | The `scope` (`paths` or `view`) and `count`, with the `paths`, or for a view the `filters` and `excluded_paths` |
| `ui_next_page` | Load the next page of the gallery |
| `ui_show_culling_group` | Open the darkroom on one group, identified by `(type, group_id)` (edition accounts) |
| `ui_show_culling_plan` | Open the darkroom on an `auto_cull` plan (`plan_digest` and `request` from the preview, optional `focus` group number), with the plan's keepers pre-selected for you to flip and confirm (edition accounts). `auto_cull` calls it for you on a dry run. The same digest as the plan already shown only moves the focus; a different one replaces the plan and is refused as `unsaved_decisions` while you hold decisions you have not confirmed, and as `plan_changed` when the library moved since the preview, and as `plan_load_failed` when the tab could not load the plan for any other reason |
| `ui_show_comparison` | Open the pairwise comparison page, optionally on one category and strategy; it only opens the page, you pick the winners |

How it works:

- While you are signed in and both `viewer.mcp.enabled` and `viewer.mcp.bridge` are true, every Facet tab opens a same-origin WebSocket to `/api/mcp/bridge` and authenticates with your session in its first message. The bridge is on by default; set `viewer.mcp.bridge` to `false` to turn it off, and the `ui_*` tools then answer a clear error.
- `ui_get_context` reads the open page, the gallery state, the selection count and the `actions` that apply to this page and token; `available_actions` answers the same question from the server for your open tab. Tools above the token's level are not listed.
- A tool only reaches the tabs of the token's owner. On a single-password install every session is the same user, and on an open install every tab belongs to the shared `_anonymous` user, edition logins included.
- Each tab carries the level of the session that opened it, and a token only drives tabs at or above its effective level: an `edition` token never uses a tab signed in with a viewer-only session, while a `readonly` token may drive an `edition` tab. On a single-password install a token is also capped by the session that minted it: a token minted from a viewer-only session reaches only viewer-level tabs, never the edition tab (a token minted before this rule is capped at its own level). On an open install a token is capped at viewer level too: it reaches only viewer-level tabs, never an `edition` tab, except the local editing tab described below. A tab can only be replaced by one of equal or higher level: a viewer-only session reusing an edition tab's `tab_id` is refused with 4409, and past the per-user tab cap the lowest-level tab goes first. `status` lists only the tabs the token can drive. `status` also reports `out_of_reach_tabs`, the number of open tabs this token cannot drive. Under `viewer.trusted_local_editing` on an open install, a tab whose handshake passes the same-machine boundary registers at `edition` and drops to `readonly` within one ping when the opt-in is turned off; LAN or forwarded tabs stay `readonly`. A token used from the local machine reaches that local editing tab whatever level it was minted at, while a token used from another machine (LAN) never reaches it and gets `no_tab`, with a message explaining that a non-local request cannot steer a local editing tab.
- With several tabs open, the most recently focused one is used and the result's `tab` field says so. Pass `tab_id` (listed by `status`) to choose another.
- A tab refuses what its account may not do (for example `/culling` for a non-edition account) and the tool returns that refusal.
- What a tab sends back is untrusted: it is bounded in depth, string length and list length, and capped by `max_bytes`.
- Errors: `no_tab` (no tab is connected, or the bridge is off), `tab_timeout` (no answer within `call_timeout_s`) and `tab_outdated` (the open tab does not know the tool; reload the page after upgrading Facet).
- The bridge accepts the WebSocket first and then refuses it with a close code rather than an HTTP status: 4404 when the endpoint or the bridge is off (the tab then stays disconnected until the page is reloaded), 4403 when the `Origin` is missing or not allowed, 4401 for a missing or rejected session.
- A reverse proxy must forward the WebSocket upgrade for `/api/mcp/bridge`; see [Deployment](DEPLOYMENT.md). If it rewrites the `Host` header, list the public origin in `viewer.mcp.allowed_origins` (for example `["https://photos.example.com"]`), because the page's origin must match the host or be listed.
- The tab registry is per process, so the bridge needs a single worker (the default).
- **What the user is doing.** `ui_get_context` also returns `focused`, `{path}` for the photo under the keyboard cursor in the gallery, the open photo on the photo page or the current photo in the darkroom (otherwise `null`; hovering does not count, switching to the assistant's window keeps it, and it clears when the photo leaves the list), and `user_activity`, `{items, until, truncated}`: what the user did in the tab (ratings, rejects, favourites, confirms and skips of an assistant plan on `/culling` (`cull_confirm`, `cull_skip`: recorded only in plan mode, once the confirm has landed or the skip countdown has elapsed; manual culling and a confirm flushed by Exit are not journalled), tags, albums, navigation), at most 50 items of 20 paths each, the newest kept. It is stateless: pass the previous answer's `until` as `activity_since` to get only what is newer; two calls without it return the same items. The assistant's own writes and its own `ui_*` navigation are never listed. The journal lives in the tab's memory and is lost on reload. The tab keeps its last 500 actions.

Beyond the basics above:

- `ui_set_gallery_filters` takes you to the gallery first when another page is open, then applies the patch. It refuses a whole patch (`invalid_input`) that names a filter the tab has no control for; use `search_photos` for those. On an album page, any change first returns to the gallery (not only `replace: true`), so the album's saved filters are not overwritten and the album scope is dropped. It also accepts `semantic_query`, `semantic_threshold` (0 to 0.5), `similar_to`, `similarity_mode` and `min_similarity` (0 to 1); `similar_to` and `semantic_query` cannot be combined.
- `ui_get_gallery_view`, `ui_next_page` and `ui_select_photos` with `select_view` need the gallery (or an album) to be the open page, otherwise they answer `no_active_view`; call `ui_navigate` to `/` first. Give `ui_select_photos` exactly one of `paths` and `select_view`.
- `no_tab` also means no Facet tab is open: open Facet in a browser and sign in. The status line in the **Connect an assistant** dialog shows whether this tab is connected; the `status` tool lists open tabs and their ids.
- A tab stops reconnecting once its session is rejected (sign in again), and waits until you return to it after another tab of yours took over.
- The tab bridge connects only when the server reports the bridge as available (the endpoint is on and `viewer.mcp.bridge` is true); with the bridge off, tabs do not connect at all.
- `ui_set_gallery_filters` refuses an unknown filter name with `invalid_input`, and also a patch giving both `category` and `type`, or both `person` and `person_id`. It offers only the filters the gallery can show; use `search_photos` for the others.
- `ui_navigate` opens only the app's own static pages: the login page, shared pages, external URLs and unknown paths are refused (`invalid_input`), and edition-only pages are refused for a non-edition session.
- `ui_select_photos` with mode `remove` under a whole-view selection ignores paths outside the loaded view and lists them as `not_in_view` in the result.

## Live updates

When an assistant changes photos through a write tool, the Facet tabs you have open follow without a reload.

- **What refreshes.** The gallery updates the changed cards in place, keeps an assistant's pinned list, and drops a photo removed from the library (`delete_photos`). A photo that `cull_apply` moved or trashed keeps its library row, so it stays in a pinned list, while views that hide rejected photos (the default) already hide it. A write that cannot name its photos (see below) reloads the view instead, keeping the current rows on screen and your selection until the new rows arrive, so the grid never blanks. Semantic-search and similar-photo views refresh the photos already shown and never remove one, including for a write that cannot name its photos. The photo page refetches its photo (a photo removed from the library takes you back). The darkroom (`/culling`) patches reject, favourite and rating in place, shows a Rejected marker and keeps your own decisions; on a change it cannot scope it reloads only when nothing is at stake, otherwise it shows a Reload banner that stays until you reload.
- **One notice per burst.** Changes are batched (400 ms trailing debounce, 2 s at most) into a single "Assistant changed N photos" notice.
- **One entry per assistant call.** A call that writes several photos appears once in the activity panel, labelled with the assistant tool's name in your language (a tool without a label shows its raw name), with the photos of the whole call counted together. Above 200 photos the entry names none, so the view reloads and the entry has no **Show photos** button. After an `auto_cull` apply, **Show photos** pins the photos it rejected (up to 200).
- **Which writes.** Ratings, favourites, rejects, tags, captions, album membership, culls, deletes, sequence and category overrides, face assignments, junk clearing and darkroom confirmations. Reads, dry runs, refused writes, album creation, metadata export and scans do not. A write that times out (`outcome_unknown`) still refreshes since the write may have landed, and a write still running at that moment shows up on the next refresh or reload.
- **Unscoped writes.** A write targeting a `filters` view, one that includes set siblings, one over 200 photos, or one that names no paths reloads the view instead of refreshing named cards.
- **The bridge must be on.** A write made over `/mcp` reaches your tabs through the tab bridge, so `viewer.mcp.bridge` must be `true`. A write made by the page itself (`POST /api/mcp/call`) is response-driven (`changed_paths`) and updates even with the bridge off.
- **Same process only.** The notice reaches only the writer's tabs connected to the same server process, so with `viewer.py --workers N` it can miss a tab (the bridge needs a single worker, the default).
- **After an upgrade, reload your open tabs.** The tool list changed, so an open tab answers `tab_outdated` until it is reloaded.

## In-page WebMCP (browser agents)

Separately from the `/mcp` endpoint, a tab that is signed in also offers the same `ui_*` tools to agents that live in the browser itself, through the W3C [WebMCP](https://webmachinelearning.github.io/webmcp/) API (`document.modelContext`). A browser-native assistant therefore sees exactly the tools listed above, runs them in the tab you are looking at, and needs no token.

- **Secure context only.** Facet registers the tools only on HTTPS or `localhost`. On plain HTTP the in-page tools are not offered; the token-based connection above keeps working.
- Registered when `viewer.mcp.enabled` is true and you are signed in, and removed when you sign out.
- The object is `document.modelContext` (the deprecated `navigator.modelContext` alias is not provided). It is a polyfill, installed only when the browser has no native one, and it cannot be uninstalled: it can exist before you sign in with no Facet tools in it, and after you sign out it stays with an empty tool list.
- The tools do the same things, and are bounded by the same account level, as in the table above.
- A browser agent reads the same `actions` list through `ui_get_context`.
- **Library tools in the page.** The tab also offers the server's own tools (search, ratings, tags, albums, darkroom, reports) through `GET /api/mcp/inpage_tools` (the list, with each tool's schema, its `required_level` and the session's current `level`) and `POST /api/mcp/call` (`{tool, arguments, selection_snapshot?}`). They run as your signed-in session through the same wrapper as `/mcp`, so levels, previews, `confirm` values and rate limits behave identically. A failed tool is a normal `ok: false` envelope (HTTP 200); a call also reports `changed` (photos written).
- **Level.** The level is the lower of the one your sign-in carries and your live role, read again on every call: a demoted account loses the writes at once and a deleted one is refused (401). Below a tool's floor the answer is `forbidden_level` ("This session's level is readonly; set_rating needs edition: unlock edition in Facet"). On a single-password install a writing session needs edition unlocked.
- **Who may call.** Only a signed-in person. An agent's own `/mcp` token is refused on these routes (403), and so is a foreign `Origin`; a cookie alone never authenticates. Every call carries an `X-Facet-Agent-Session` header (1 to 64 letters, digits, `_` or `-`; a missing or malformed one answers 400). It tells tabs apart, so a `confirm` value issued to one tab is refused to another; the page chooses it, so it separates, it does not authenticate.
- **What is left out.** The image tools (`get_thumbnail`, `contact_sheet`) and `available_actions` (use `ui_get_context`). A tool's `show` argument is always off, because the tab is the caller, and `tab_id` is refused. `status` reports only the server and UI-contract versions. `target: "selection"` uses the `selection_snapshot` the page sends (what `ui_get_selection` returned) and is `invalid_input` without it. Destructive actions still follow `viewer.mcp.allow_destructive`.
- **Taste.** Like any assistant write, a tool call made from the page never records comparisons and never arms the retrain.
- **Switch.** `viewer.mcp.inpage_tools` (default `true`) turns both routes off (404) and clears `features.mcp_inpage` in `/api/auth/status`; `viewer.mcp.enabled: false` turns them off too.

## Changing things

Write tools sit next to the read tools in the same `/mcp` list. Each one goes through the viewer's own `/api` routes, so the route's guards still apply, and each counts against the `write_rate_per_min` budget. The level is the lowest effective level that may call the tool (see [Permission levels](#permission-levels)).

| Tool | Level | What it does | Caps |
|------|-------|--------------|------|
| `set_rating` | `user` | Set the star rating (0-5) of photos | 50 paths |
| `set_favorite` | `user` | Mark or unmark photos as favourite (marking clears rejected) | 50 paths |
| `set_rejected` | `user` | Reject or un-reject photos (rejecting clears rating and favourite) | 50 paths |
| `batch_set_rating` | `edition` | Set the rating of many photos | 1000 paths, or `filters` |
| `batch_set_favorite` | `edition` | Mark many photos as favourite | 1000 paths, or `filters` |
| `batch_set_rejected` | `edition` | Reject many photos | 1000 paths, or `filters` |
| `add_tags` | `edition` | Add manual tags (kept apart from the AI tags) | 10 tags; 1000 paths, or `filters` |
| `remove_tags` | `edition` | Remove manual tags | 10 tags; 1000 paths, or `filters` |
| `create_album` | `edition` | Create an empty album (not idempotent: twice makes two albums) | |
| `album_add_photos` | `edition` | Add photos to an album (already present ones are ignored) | 1000 paths |
| `album_remove_photos` | `edition` | Remove photos from an album; the photos are untouched | 1000 paths |
| `assign_faces` | `edition` | Move faces to a person; faces another person owns are left alone unless `allow_reassign` is set, and the result lists what was skipped | 50 face ids |
| `set_caption` | `edition` | Set a photo's caption (set semantics; an unchanged caption comes back as `already`) | 1 photo, 2000 characters |
| `export_metadata` | `edition` | Write XMP sidecars next to the files | 100 paths, or `filters`, or `target` |
| `junk_list` | `readonly` | List junk-sweep candidates, optionally of one `kind` | 100 per page |
| `junk_reject` | `edition` | Reject junk-sweep candidates (same as `batch_set_rejected`) | 1000 paths |
| `junk_clear` | `edition` | Keep candidates: mark them evaluated-clean so they leave the queue | 50 paths |
| `cull_apply` | `edition` | Copy the keepers, or move or trash the rejects ([preview then confirm](#destructive-actions-preview-then-confirm)) | 10000 paths, or `filters` |
| `delete_photos` | `edition` | Trash the files and delete their library rows ([preview then confirm](#destructive-actions-preview-then-confirm)) | 1000 paths |

- **The `user` tools need an edition token on a single-password install**, which has no middle level (see [Permission levels](#permission-levels)).
- **Set semantics.** The per-photo tools read the current state and write only a difference, so repeating a call is harmless; each path reports `changed` or `already`. They run one path at a time and stop at the first `library_busy`, `outcome_unknown` or `forbidden_level`, reporting `affected`, the per-path `results` and `not_attempted`. The batch tools set the same state.
- **Choosing the photos.** The batch, tag and `cull_apply` tools take EITHER `paths` OR `filters` (the `search_photos` filter object), plus an optional `exclude` list. A `filters` target must come with `expected_count`, the match count of the filters before `exclude` is applied (`search_photos` `total`). Facet counts the filters again first and writes nothing when the numbers differ (`invalid_input`, with `actual_count`). The viewer's default hide toggles (including rejected photos) apply to `filters` exactly as in `search_photos`, so its `total` is the `expected_count`. Rejected photos are therefore hidden from a `filters` target: for `move_rejects` and `trash_rejects`, pass `show_rejected` (or `hide_rejected: false`) to BOTH `search_photos` and `cull_apply`; `copy_keeps` needs nothing extra.
- **Whose state.** Ratings, favourites and rejections are the token owner's own.
- **Skipped files.** When `cull_apply` or `delete_photos` reports a non-empty `skipped` list, the result also carries a `skipped_reason`: those library paths have no readable file on disk (missing, moved, or outside the scan directories), and nothing was done for them.
- **The photos the user selected.** Where a tool takes `paths`, `target: "selection"` uses the selection of the open tab instead (`tab_id` picks the tab). A selection that changed between the preview and the confirm answers `invalid_input` with `selection_changed`, a selection too big for the tab's reply answers `too_large`, and `delete_photos` re-reads the selection when you confirm.
- **Captions and exports.** `set_caption` stores the text only. The caption is not re-embedded, so semantic caption search keeps matching the old text until a re-embed, and the incremental viewer-database export keeps an existing caption when the source one is empty, so a cleared caption may come back with a later export or scan. `export_metadata` waits up to 180 seconds, reports `written`, `skipped` and `errors` with the first error text in `first_error`, and refuses to write with exiftool 13.23 to 13.27.
- **Faces.** `assign_faces` skips, and lists, faces that are missing, already on that person, owned by another person (unless `allow_reassign`), on another embedding model or on a hidden person; `assigned_count` is what actually moved.

### Destructive actions: preview then confirm

`cull_apply` (`copy_keeps`, `move_rejects`, `trash_rejects`) and `delete_photos` are flagged `destructiveHint` and run as a dry run unless called with `dry_run: false`.

1. The dry run changes nothing and lists the files it would copy, move or trash (long lists are cut to `max_rows`, with a `<key>_count`). For `move_rejects`, `trash_rejects` and `delete_photos` it also returns a `confirm` value, valid for `confirm_expires_in_s` (5 minutes) and for one use.
2. The real call (`dry_run: false`) must pass that `confirm`. Facet re-resolves the file set and options and compares them with the ones the value was issued for. If anything changed, the value is void and the call answers `confirmation_required`: dry-run again.
3. `copy_keeps` needs no `confirm`: it only writes copies. It still previews by default.

The `confirm` value is bound to the token, the action and the exact file set plus options. It lives in memory in one process, so a restart discards every pending value.

**Recommended practice:** always show the user the dry-run summary (counts and file list) and get explicit approval before the `dry_run: false` call. Never confirm on your own initiative.

- `move_rejects` and `trash_rejects` act only on photos the owner rejected; any others are reported as `excluded_by_state`. Companion RAW and `.xmp` files (`include_companions`) and the other frames of a bracket or panorama (`include_sequence_siblings`) are untouched unless you opt in.
- `delete_photos` sends the files to the OS trash and **deletes their library rows**: the scores, tags and ratings are not recoverable, even when the files are.
- **Prerequisites.** `trash_rejects` and `delete_photos` need `viewer.cull.allow_trash` set to `true` (default `false`; the call is refused otherwise). The `target_dir` of `copy_keeps` and `move_rejects` must sit under an allowed export location: `viewer.export.allowed_target_dirs` plus your scan directories (see [Export and Cull Destinations](CONFIGURATION.md#export-and-cull-destinations)).

## Corrections and reference data

- **Corrections** (`edition`). `override_sequence` (`kind`: `panorama`, `bracket`, `hdr_panorama` or `suppress`; at least 2 paths except for `suppress`) and `clear_sequence_override` record a correction that takes effect at the next detection pass (the result reports `pending`). `override_category` and `clear_category_override` set or clear a sticky category that survives rescans and keeps the scoring context.
- **Comparing frames** (`readonly`). `group_compare` compares the frames of one culling group (up to 12 paths) `by: "faces"` (per frame: face count, blinks, worst eyes-open, best smile, `best_path_by_eyes`) or `by: "subjects"` (subject sharpness and prominence, `sharpest_path`). It is advice for you, not a decision. `cull_report` summarises a scope in one call: total, kept, rejected, favourites, rated, unreviewed, what the hide toggles would hide, junk, low scores, the top keepers and, with an edition token, the first darkroom sets. Reasons overlap. It carries a `basis` stating which filters each count honours (the hide toggles are not applied to the counts).
- **Taste.** `comparison_status` (`edition`) reports how many pairwise comparisons you have made and how well they cover the library. No tool submits, edits or deletes a comparison: the answer to a pair is your own click. Writes made by an assistant (ratings, rejections, darkroom confirms, `auto_cull`) never record comparisons and never arm the automatic retrain; the same action made by you in the gallery still does. The ratings, favourites and rejections an assistant wrote are also kept out of the personal ranker's training pairs when it is rebuilt from your ratings; they count again once you rate that photo yourself. That record is kept in its own table and is never exported.
- **Scans.** `start_scan` and `scan_status` (`edition`) start and follow a scan of the configured directories. They are listed only when `viewer.features.show_scan_button` is on and the install is locked (a superadmin key in multi-user mode), or to a Full-editing local token under `viewer.trusted_local_editing`, which does not need `show_scan_button`. A scan is additive and is refused while another job runs (`conflict`). Syncing with Immich stays on the command line.
- **Resources.** Besides tools, the server lists five read-only `facet://` resources: `facet://categories`, `facet://tags`, `facet://persons`, `facet://filters` (every search filter with its value domain, plus the metric ranges) and `facet://scoring-contexts`. Each is read as the key's owner sees the library and is capped at 200 rows and 32 KiB (`truncated` says so).
- **Choosing what is listed.** `viewer.mcp.tool_profile` is `full` (default) or `core`: `core` lists only an 11-tool set for small models (`status`, `search_photos`, `semantic_search`, `get_photo`, `filter_options`, `library_stats`, `ui_show_photos`, `set_rating`, `set_favorite`, `set_rejected`, `album_add_photos`). It changes the listing only, never what a key may call. `viewer.mcp.allow_destructive` (default `false`) gates `delete_photos` (not listed when off), the `move_rejects` and `trash_rejects` actions of `cull_apply`, and `assign_faces` with `allow_reassign`; refused calls answer `feature_disabled`. Tools a token's level cannot call are not listed either.
- **Two more error codes.** `feature_disabled`: the route is switched off by a configuration key, and the message names it. `conflict`: the library is busy with a job that excludes this one (for example a scan already running).

## Darkroom (culling groups)

The darkroom tools mirror the `/culling` page. All of them need the `edition` level, including the listing ones.

| Tool | What it does |
|------|--------------|
| `list_culling_groups` | List groups (`burst`, `similar`, `scene`, `bracket`, `panorama`, `hdr_panorama`) with their photos and scores, sortable and scoped by album or date window |
| `culling_profiles` | The genre-aware culling presets and the default one |
| `suggest_culling_profile` | Name the preset that fits an album or a capture-time window |
| `keeper_hints` | Per-photo "a better shot exists in this burst" hints for up to 100 paths (empty when no keeper head is trained) |
| `auto_cull` | Auto-cull a scope under a keeper budget: preview the plan page by page, then apply it with the `confirm` value |
| `confirm_culling_groups` | Confirm up to 20 groups: keep their `keep_paths`, reject the rest of their `paths` |

- **A group is identified by the pair `(type, group_id)`**, never by `group_id` alone: similar-group ids are offset when merged with bursts.
- **The default `group_by: "all"` returns bursts plus similar groups only.** Ask for `scene`, `bracket`, `panorama` or `hdr_panorama` explicitly.
- **A page is trimmed to fit `max_bytes` by shortening each group's `photos` list, never by dropping groups.** `photo_count` stays the true size, `photos_truncated` marks a group whose list was cut, and `has_more` says whether another page follows.
- **Brackets, panoramas and HDR panoramas are kept whole.** In `confirm_culling_groups`, `keep_paths` must equal `paths` for these types (otherwise `invalid_input`), and `auto_cull` never splits them.
- **Empty `keep_paths` rejects every frame of the group.** The first call then answers `confirmation_required` with a `confirm` value; show the user, then repeat the call with it. If a batch stops on `forbidden_level`, `library_busy` or `rate_limited`, the groups already done are reported.
- **`auto_cull` previews by default** and returns the keep and reject split per group plus a `confirm` value (only when something is left to reject). Every call plans the whole scope and returns it in pages of whole groups (the route pages at 200 photos, but a single larger group gets its own page, and the tool may return fewer groups to fit the result size): repeat the call with `cursor` set to the previous `next_cursor` and `plan_digest` set to the cursor-0 page's `plan_digest` (required when `cursor` > 0) until `next_cursor` is `null`. A plan that changed since the first page is refused as `confirmation_required`: restart from cursor 0. Each row carries its plan-wide `number`, and `kept` and `rejected` cover the full plan. Cull a whole date range in ONE call, never month by month.
- **One `confirm` covers the full plan** (valid 300 s, single use). The apply re-computes the plan and refuses it as `confirmation_required` if it changed since the preview. Rejections made by an assistant never feed the personal ranker, unlike the same cull made by you in the gallery. The `confirm` is issued on the cursor-0 page only. The apply returns counts only (`groups_processed`, `kept`, `rejected`, `highlights_added`).
- **Overrides.** `keep_paths` and `remove_paths` (up to 1000 each) override single frames of the plan. Pass the same overrides on the dry run that issues the `confirm` and on the apply. Paths that are not in the plan are ignored and reported as `ignored_overrides` (the first 20, with `ignored_overrides_count`). Removing a frame the plan KEEPS in a bracket, panorama or HDR panorama set, leaving a group without a keeper, or listing a path in both lists is refused as `invalid_input`, naming the paths or groups; removing a frame the plan already rejects is a no-op. The set rule applies to groups made entirely of one set kind: a group mixing ordinary frames with set frames is not kept whole, so its frames can be overridden like those of any burst.
- **The user's flips are not read back by the apply.** The apply never reads the tab. To honour what the user changed on the plan, read `ui_get_context.culling.changed` and pass those groups' `keep_paths` / `reject_paths` as `keep_paths` / `remove_paths` on the next dry run and on its apply (the lists must be the same on both). A group the user confirmed in the tab leaves the plan: the plan digest moves, so a pending `confirm` is refused as `confirmation_required` and you preview again; the new preview no longer contains the confirmed groups, and you never re-decide them.
- **If the user changes something between preview and apply.** The apply is checked against the preview. A photo whose rating, favourite or reject state the user changed since the preview is left out and reported as `skipped_user_changed` (the first 50 paths, with `skipped_user_changed_count`); a group left without a keeper is skipped whole and counted in `skipped_user_changed_groups`. The per-photo skip applies only when neither `keep_paths` nor `remove_paths` is given; with explicit lists the apply re-runs the dry run and any plan change, a manual reject included, is refused. A rating, favourite or reject written by anyone between the preview and the apply, the assistant's own writes included, counts as a change. A plan change not explained by such photos is still refused as `confirmation_required`. When the server no longer holds the preview (older than 15 minutes, evicted, or held by another process), the answer says `state_guard: "unavailable"` and the all-or-nothing refusal applies. The guard covers assistant requests only; the command line `--auto-cull` is unchanged. The guard remembers plans of up to 12000 photos in all pages; a larger plan is not remembered, the preview says `state_guard: "unavailable"` and the all-or-nothing refusal applies.
- **`scope_dependent_kinds`** names the group kinds (`similar`, `scene`, plus `bracket` when `trim_brackets` is on) whose membership depends on the date range or the candidate pool, with a note to cull the whole range in one call. Bursts and panoramas do not change with the range, and neither do brackets unless `trim_brackets` is on.
- **`show`** (default `true`, with `tab_id`). On a dry run the plan opens on the user's `/culling` page through `ui_show_culling_plan` (see Plan mode on `/culling` above), and the result carries `shown_in_tab`: `{"applied": true, ...}` or `{"applied": false, "reason"}` with the reasons of a failed show and, specific to the plan, `unsaved_decisions` (the user holds decisions on the page they have not confirmed), `plan_changed` (the library moved since the preview) and `too_large` (the overrides are too big to send to the tab). A plan that fails to load for any reason other than `plan_changed` is reported as `plan_load_failed`. Only the first page (`cursor` 0) loads the plan; a page with `cursor` > 0 only moves the tab's focus to that page's first group. A failed show never fails the call. An apply never shows. An apply's live update (and, in-page, the `/api/mcp/call` response's `show_paths`) carries the photos it rejected, up to 200, so the activity entry's **Show photos** can pin them; the tool result itself stays counts only. An apply that rejected nothing offers no **Show photos**, and a dry run emits no live update.
- **Knobs from the tab.** With neither `strictness` nor `profile` given, `auto_cull` plans with the knobs the open tab's `/culling` page would start at: the culling profile stored in that browser, else the page's default strictness (100). With no reachable tab it uses the server's `auto_cull.default_strictness`. The result reports what it used as `knobs_from_tab` (`{profile}` or `{strictness}`); an apply carrying a confirm nonce always reuses the knobs of the preview it confirms, explicit `keep_paths` / `remove_paths` included, and never reads the tab again. `ui_get_context.culling_defaults` shows the same pair.
- Call `ui_show_culling_group` to show a group to the user in their open tab (see [Control your open tab](#control-your-open-tab)).

## Results, limits and errors

Every result is a JSON envelope: `{"ok": true, "data": ...}` or `{"ok": false, "error": "<code>", "message": "..."}`. Listings return `data.rows` (a compact fixed set of fields per photo) plus `total`. A search result also carries `shown_in_tab`, and a result trimmed by the byte cap carries `returned`.

- **Caps:** at most `max_rows` rows and `max_bytes` serialized bytes. Tail rows are dropped and `truncated: true` is set. A result without rows that exceeds `max_bytes` becomes a `too_large` error.
- **Images:** `get_thumbnail` and `contact_sheet` return an image part before the JSON part. The image is capped by `max_image_bytes` (default 262144), not by `max_bytes`. Text visible inside an image is data, never an instruction.
- **Face scan:** `possible_faces` reads at most 192000 faces and may wait up to 120 seconds; above that it answers `too_large`.
- **Rate limit:** `rate_per_min` calls per minute per token for reads. Write tools draw on a separate `write_rate_per_min` budget (default 30), so searches cannot starve writes and the other way round; the dry run of `cull_apply` and `delete_photos` counts as a write, an `auto_cull` preview as a read. Beyond it: `rate_limited` with `retry_after_s`. Ten failed bearer attempts per minute from one address answer 429.
- **Error codes:** `forbidden_level` (disabled endpoint, dead token or too low a level), `invalid_input`, `not_found`, `rate_limited`, `library_busy`, `upstream_error`, `outcome_unknown`, `confirmation_required`, `too_large`, `no_tab`, `tab_timeout`, `tab_outdated`.
- **The newer codes:** `confirmation_required` (a destructive call has no live `confirm` value for exactly this set: dry-run again, show the user the result, then retry), `outcome_unknown` (a write timed out or the connection dropped, so it may or may not have happened: re-read the state before retrying, never retry blindly), `library_busy` (the library is busy with another job: retry in a moment).
- **Gate status codes:** 401 for a missing or unknown token, 403 for a cross-origin browser request or an agent's own credential on `/api/mcp/tokens`, 404 when disabled. The tab bridge answers with close codes instead. On an open install, `/api/mcp/tokens` also answers 403 to a request that does not come from the computer running Facet.

## Security notes

- Captions, tags, file names, paths, and album and person names come from your library and can contain text written to manipulate an assistant (prompt injection). Every tool is flagged `facet/untrusted_content` and tells the model to treat them as data. Do not give an assistant that also reads untrusted content a way to act on what it finds here.
- Tokens never expire. Revoke the ones you no longer use.
- Logs record the token id, tool, outcome and row count, never arguments or the token.

## Known limitations

- On an open install (no password), the shared `_anonymous` tokens can be minted, listed and revoked only from the computer running Facet (or in an edition session when `viewer.edition_password` is set); any other request gets 403, so a peer on the network cannot fill the 20-token cap. `/mcp`, the in-page tools and the tab bridge stay reachable by anyone who can reach the viewer, as the same anonymous principal: set a password before enabling the endpoint on a network. The tab bridge widens this: a non-browser client can send a made-up `Origin` and a null token, register a focused `_anonymous` tab, answer `ui_*` calls with data of its choosing, and evict real tabs through the 8-tab cap. Under `viewer.trusted_local_editing`, a local process can also register a fake `edition` tab (it can forge `Host` and `Origin` on the WebSocket), but it could already act as the browser; a LAN client cannot, since a loopback peer is required.
- Rate limits and failed-authentication counters live in memory in each process; with `viewer.py --workers N` each worker counts separately.
- The tab registry lives in memory in one process. Use a single worker (`viewer.py --workers 1`, the default) when you rely on `ui_*` tools; with several workers a call can reach a process that does not know your tab and answers `no_tab`.
- A user can have at most 8 tabs connected; opening a ninth closes the oldest.
- Nothing is pushed from the tab to an external assistant: it learns about the user's plan progress and activity only by calling `ui_get_context`. The `auto_cull` apply does not read the tab.
- The `auto_cull` state guard keeps 8 plans per user for 15 minutes; the tool's preview memory is separate and lasts 300 seconds, holding 64 entries across all users. Both live in the memory of one process. With several workers an apply can reach a process that holds none; the answer then says `state_guard: "unavailable"`.
