## Objective + success criteria
- E1: after the user creates / renames / deletes an album, adds photos to one, assigns a face, merges / splits / renames / hides / deletes persons, rejects or clears junk, answers a comparison pair, or changes gallery filters, the next `ui_get_context` (with `activity_since`) lists one entry per action with ids and counts; photo paths appear only for photos the user acted on, and any `name` / path in an entry is untrusted data (documented as such).
- E2: a burst of filter edits (typing a search, dragging a slider) yields ONE `filters` entry, whichever store entry point made them; filter changes made by a UI tool or a server-side `show` yield NONE, including when the debounce flush lands after the tool finished.
- E3: no assistant-originated write is journalled (same rule as today).
- F1: `list_albums`, `list_persons`, `junk_list` take `show` (default false, opt-in) and, when true, open `/albums`, `/persons`, `/junk` in the user's tab with the page state set to exactly the query (an empty query clears a previous search; other page filters reset to defaults); the result carries `shown_in_tab` with the same reasons as a search (`comparison_open`, `modal_open`, `unsaved_decisions`, `navigation_refused`, `forbidden`, `no_tab` ...).
- F2: `get_photo`, `get_thumbnail`, `contact_sheet`, `junk_reject` accept `target="selection"` (+ `tab_id`), with the same trust rules as the write tools (`api/agent/target.py`); `junk_reject` additionally refuses unless the tab is on the gallery route.
- Contract JSON (regenerated: the `ui_get_context` description changes, so `ui-tools.schema.json` and its `version` hash change in commit 1), `available_actions` rows, INSTRUCTIONS, tool descriptions, docs in 7 languages and tests move in the same commit as their behaviour; `venv/bin/python scripts/dump_ui_tools.py --check` is clean after each commit.

## Design decisions (recommended)
**E**
- Kinds: ADD `person`, `junk`, `compare`, `filters`; REUSE `album` with `value.action` in `create|rename|delete|add|remove` (the existing `add` entry keeps its shape `{album_id, action}`). Four new kinds beat one per verb: the model reads `kind` first, `value.action` second.
- Values carry ids and counts, not content: `album` `{album_id, action, name?}`, `person` `{action: assign|unassign|merge|split|rename|hide|unhide|create|delete, person_id?, pairs?, count?, partial?, name?}`, `junk` `{action: reject|clear, count, partial?}`, `compare` `{category, winner: 'a'|'b'|'tie'|'skip'}` (`tie` per `submitComparison`), `filters` `{changed: {key: scalar}}` or `{reset: true}`. `name` appears ONLY for create/rename, capped at 80 chars. Paths and names in entries (acted photo paths, typed names, search text) are UNTRUSTED DATA, the same rule as library names in tool results; the docs say so. Person/album names read back from the library are never copied. `paths`: junk -> the acted paths (cap 20), compare -> `[a, b]`, assign/unassign -> the photo's path, others `[]`.
- Partial failures record what SUCCEEDED: a batch/chunked action that fails midway records the succeeded count (and paths) with `partial: true`; nothing succeeded records nothing. Merge records `count` (merges done) and, for a single merge, `pairs: [[source_id, target_id]]` (batch: `count` only), never a lone `target_id`.
- Filter changes: ONE private helper in `GalleryStore` (`journalFilters(before, after)`) is called by every user filter entry point (`updateFilter` :1026, `updateFilterDebounced` :1059 at its commit point, `updateFilters` :1081, `resetFilters` :1124). The diff is the FULL `filters()` signal before vs after the edit (so `semanticSortPatch` / `exclusiveHidePatch` side-changes are included), minus `page`, `per_page`, sort-only changes and `DISPLAY_OPTION_KEYS` / `DISPLAY_ONLY_KEYS` (layout noise); an empty diff records nothing. `resetFilters` records `{reset: true}` (no diff: a reset to defaults is one gesture).
- Suppression is decided at EDIT time: `journal.recordFilters(diff)` returns immediately when `suppressed > 0`, so an assistant-driven change is never buffered. A buffered (user) entry flushes after a 1 s trailing debounce and the flush WRITES UNCONDITIONALLY through an internal `append()` that bypasses the global `suppressed` check (otherwise a user's edit made just before a tool call would be lost; deciding at flush time would conversely let the agent's change in). Consecutive edits inside the window merge their keys (last value wins).
- Ordering: `since()` flushes the pending filter entry first, and `record()` of any OTHER kind flushes the pending filter entry first, so `seq` stays chronological and a read right after typing sees it.
- Retention/size: unchanged (500 in memory, 50 per report, 20 paths, byte-trim server side). `filters` values: scalars only, strings capped at 80 chars, at most 12 keys per entry (`truncated` is not needed; extra keys dropped). Reload still loses the journal (documented).
- Why not an effect on the `filters` signal: it would fire for URL restores, store resets on identity change, and every assistant patch; entry-point recording is the established rule (journal doc comment).
**F**
- "show" per tool, using the existing `ui_navigate` (no new ui tool, no contract change): `list_albums` -> `/albums` with the search; `list_persons` -> `/persons` with the search; `junk_list` -> `/junk` with `kind`; `junk_list` with `page > 1` and `show=true` is NOT shown (`shown_in_tab: {applied: false, reason: "page_not_first"}`, the existing reason searches use for a later page, `tools_read.py:182`), because the junk page always starts at page 1. Opening a single album is B's `ui_open_album`, NOT a `show` (the model chains `list_albums` -> `ui_open_album`).
- **Default `show=false` (opt-in) for these three**, unlike searches. Justification: a search's result IS what the user asked to see and a shown search is idempotent, whereas `list_albums` / `list_persons` / `junk_list` are mostly name->id lookups feeding the next call (`ui_open_album`, `album_add_photos`, `junk_reject`); auto-navigating on every lookup would yank the user off their page twice in a chain and trips the D `unsaved_decisions` guard on `/culling`. INSTRUCTIONS gains one sentence: "List tools (list_albums, list_persons, junk_list) show their page only with show=true: pass it when the user asks to see them." `possible_faces` keeps its default true (rows are photos).
- `list_culling_groups`: NO `show`. The `/culling` darkroom feed does not take `group_by`/`sort`/`album_id` from the URL, so a "show" would navigate without applying the query - exactly the mismatch the results would contradict. The existing `ui_show_culling_group {type, group_id}` and the `auto_cull` plan show are the right primitives; mention it in the tool description. Revisit only if `/culling` gains query params.
- Query application needs one small client change: the three pages read an initial `search` (albums, persons) / `kind` (junk) query param ONCE on init into their existing signals (`albumsFilters.search`, `PersonsFiltersService.search`, `activeKind`), and `ui_navigate` already forwards `query`. Alternative rejected: a new `ui_set_list_search` tool (a 16th+ tool for three strings). `ui_navigate` navigates with `onSameUrlNavigation: 'reload'` (`ui-tool-handlers.ts:345`), so even an identical URL re-emits; the pages subscribe to `queryParamMap` (not a snapshot) and treat the params as AUTHORITATIVE on every emission: the page state is set to exactly the query. An empty `search` CLEARS the search (the server always sends the param, empty string allowed), albums `typeFilter`/sort and persons `showHidden` reset to their defaults, and junk `kind` is applied after the kind list loads. Applying it in full is what makes the rows the assistant listed equal the rows the user sees.
- Relay: add `show_route_in_tab(registry, resolved, settings, tab_id, route, query, *, timeout)` to `api/agent/show.py` built on `_show` with tool `ui_navigate` and `UiNavigate.model_validate({"route":..., "query":...}).forward()`; success `{applied: True, tab_id, route, keys: <query keys>}`. Empty result (`rows == []`) -> `not_shown("empty_result")` like searches (do not navigate to an empty page for a typo). `_tag_mode`-style `mode: "route"`.
- `target="selection"` for reads: one helper in `api/agent/target.py`, `resolve_selected_paths(registry, resolved, settings, tab_id, *, cap, exact_one=False)` -> `(error, paths, meta)` reusing `read_selection` (so the same truncation/count/tamper checks apply). Whole-view selections expand via `/api/photos/paths` exactly as `resolve_selection(need_paths=True)` does; `exact_one` (get_photo, get_thumbnail) answers `invalid_input` "Select exactly one photo" for 0 or >1. `contact_sheet`: cap `MAX_SHEET_PATHS`, error text names it. `junk_reject`: through `resolve_target` (so `exclude`/`expected_count` are refused with a selection, same as `batch_set_rejected`), cap `BATCH_CAP`; it ALSO refuses unless the tab's route is the gallery (mirrors `target="view"`'s `data.get("route") != VIEW_ROUTE` check, `target.py:233`, same `invalid_input` code via the same refusal helper), because on `/junk` the selection the tool would read is not the junk page's own. `get_photo` / `get_thumbnail` / `contact_sheet` are read-only and may read the gallery selection from any route; the tool descriptions and docs say so. Exactly one of `paths` / `target` (these tools never take `filters`; `resolve_target` already says so). `data.target` meta is attached on success (`_with_target` for junk_reject; for the image tools, a text note in the result - the image envelope has no `data`, see step 7 risk).
- Interactions: C's `modal_open` -> `shown_in_tab.reason = "modal_open"`, nothing navigates, the list still returns; D's guard -> `reason: "unsaved_decisions"` (leaving `/culling` with unconfirmed decisions) - documented, no new code; `/compare` -> `comparison_open` (the shared guard). `/junk` and `/compare` are edition-only: a non-edition user's tab answers `forbidden_level`, mapped to `reason: "forbidden"`; for `junk_list` that is already the level of the tool itself, so the case is rare but handled. `comparison_open` blocks `show` on `/compare` only; `target="selection"` has no such interaction (read-only).

- `compare`: answering a pair writes a training comparison; recording `winner` reveals the user's taste to the assistant - intended ("what did I just do"), but `skip` is recorded too so a model cannot infer unseen pairs.
- Bulk persons actions (batch merge / delete) record ONE entry with `count`, never one per id, to protect the 50-item window from a single click.
- `get_photo`/`get_thumbnail` with `target="selection"` and a whole-view selection of 1 photo: resolved through the paths expansion; a view of N>1 is refused (`invalid_input`), not silently the first.
- Image tool results are `CallToolResult` with image content, not `{ok,data}`: `target` meta is appended as a leading text block; if `images.py` cannot take it cleanly, drop the meta (not load-bearing) and say so in the description.
